# AI 작업 기록

AI가 틀렸거나 내가 방향을 바꾼 지점. 형식: 무엇이 틀렸나 / 어떻게 확인했나 / 어떻게 고쳤나.

## 2026-11-12 (1단계)

### 방향 변경: dio를 빼고 supabase_flutter만 쓰기
- **제안:** AI가 스택에서 dio를 빼자고 했다. 처음엔 "Flutter에서 dio는 거의 다 쓰는데, 실서비스 수준에 맞나?" 하고 의심했다.
- **확인:** 백엔드 개발자가 만든 API를 부르는 상황과 Supabase를 쓰는 상황을 나눠서 비교했다. dio로 Supabase REST를 직접 부르면 토큰 갱신을 다시 만들어야 하고, 로그인 때문에 SDK도 결국 필요하다.
- **결정:** supabase_flutter만 쓴다. 호출은 저장소 클래스 안에 가둬서 나중에 바꿀 수 있게 한다.

### 틀림: 최신 Riverpod 버전이 최소 Flutter(3.38)에서 설치되지 않음
- **틀린 것:** 처음 `pub add`에서 최신 범위(`riverpod_annotation ^4.0.3`, `json_annotation ^4.12.0`)를 그대로 박았다. 전역 메모의 "flutter_riverpod 3.4"도 3.38에서는 안 된다.
- **확인:** Flutter 3.38.10으로 `pub get` → `riverpod_generator`가 `meta ^1.18.0`을 요구하는데, Flutter 3.38 SDK는 `meta 1.17.0`에 고정돼 있어서 실패했다. `flutter_riverpod 3.4.1+`도 Dart 3.12 이상을 요구한다.
- **고친 것:** 하한을 `flutter_riverpod ^3.0.0`, `riverpod_annotation ^4.0.0`, `json_annotation ^4.9.0`, `freezed_annotation ^3.0.0`으로 낮추고 3.38에서 다시 풀었다. 결과: riverpod 3.1.0 / generator 4.0.0+1 / freezed 3.2.3 / json_serializable 6.11.2.

### 틀림: 시드 데이터의 단계 날짜가 거꾸로 감
- **틀린 것:** 시드에서 고래헬스를 "관심 10/28 → 지원 10/26"으로 넣었다. 등록일은 15일 전, 지원일은 17일 전으로 숫자를 잘못 골랐다.
- **확인:** `db reset` 뒤 이력을 공고별로 조회해서 날짜 순서를 눈으로 확인했다. 테스트는 다 통과한 상태였다.
- **고친 것:** 시드 숫자만 고치면 앱에서 날짜를 직접 고를 때 같은 일이 또 생긴다. 그래서 트리거에 "이전 단계보다 빠른 날짜는 거부" 규칙을 넣었다. 먼저 이 경우를 pgTAP 테스트로 추가해서 고치기 전에 실패하는 것을 확인했다. 그런 다음 트리거와 시드를 고쳤다.

### 방향 변경: 이전 Flutter 버전 확인을 빼고 freezed 4로
- **변경:** 지시서에는 "fvm으로 낮은 버전 확인"이 있었지만, 개인 프로젝트라 필요 없다고 판단해서 뺐다.
- **확인:** 최신으로 올려 보니 freezed 3이 analyzer를 옛 버전에 묶어서 riverpod 3.3.2까지만 올라갔다. freezed는 시험판(3.2.6-dev.1)이 깔렸다(`flutter pub outdated`).
- **결정:** freezed 4로 바꿨다. riverpod 3.5 / generator 4.0.10 / go_router 18 모두 정식판.

### 틀림: 단계 이력이 최신순으로 거꾸로 옴 (2단계)
- **틀린 것:** 저장소에서 `.order('changed_at')`을 오름차순으로 생각하고 썼다. supabase-dart(postgrest)의 `order()`는 **기본이 내림차순**이다(SQL `ORDER BY`와 반대).
- **확인:** 로컬 Supabase에 실제로 붙는 저장소 테스트에서 이력 순서가 `[관심→지원, 없음→관심]`으로 나와 실패했다. 쿼리 체인을 가짜로 흉내 냈다면 못 잡았을 버그다.
- **고친 것:** `ascending: true`를 명시했다. 같은 테스트가 통과하는 것을 확인했다.

### 틀림: 웹 "새로 고침" 버튼이 눌러도 아무 반응이 없어 보임 (3단계)
- **틀린 것:** 버튼을 누르는 동안만 "새로 고치는 중…"을 보여 주게 만들었다. 로컬에서는 요청이 몇 밀리초 만에 끝나고 데이터도 같아서, 화면에 아무 변화가 없었다. 새로 고침이 실패하면 보이던 목록이 통째로 에러 화면으로 바뀌는 문제도 있었다.
- **확인:** 사용자가 "버튼 피드백이 없다"고 알려 줬다. Supabase 입구(Kong) 로그를 보니 누를 때마다 `GET /rest/v1/job_postings 200`이 찍혀 있었다. 동작은 했고, 보이는 피드백이 없었던 것이다.
- **고친 것:** "HH:MM:SS 업데이트" 시각을 표시해서 누를 때마다 바뀌게 했다(TanStack Query의 `dataUpdatedAt`). 목록이 이미 있으면 새로 고침이 실패해도 목록은 두고 위에 안내만 띄운다.

### 틀림: 대시보드 막대가 안 보이고 화면이 검게 나옴 + 서버 에러를 못 봄 (3단계)
- **틀린 것:** 1) 차트 색과 "밝은 화면 고정"을 `globals.css`에 넣었는데, 실행 중이던 개발 서버가 그 수정을 반영하지 못해 예전 CSS(다크 모드 규칙, 색 변수 없음)를 계속 보냈다. 막대 색이 "없음"이 되어 투명해졌다. 2) 대시보드의 "오늘 날짜"와 TanStack Query 안의 현재 시각이 Next.js 16의 "미리 만드는 틀에서 지금 시각 금지" 규칙에 걸려 서버 기록에 에러가 찍히고 있었다.
- **확인:** 사용자가 보낸 캡처(검은 배경, 막대 없음). 내가 한 확인은 HTML 글자(숫자)뿐이라 두 문제 모두 놓쳤다. 서버가 보낸 막대 HTML은 정상(높이 100%·50%)이었고, 보내는 CSS를 받아 보니 색 변수가 없었다. 개발 서버 기록에서 `encountered the unstable value Date.now() while prerendering`을 찾았다.
- **고친 것:** 개발 서버를 껐다 켜고 캐시(`.next/dev`)를 지워 새 CSS가 나가는지 확인했다. 시각을 쓰는 부분 앞에 `await connection()`("요청 때 만든다")을 넣었다. 다음부터는 화면을 바꾸면 숫자뿐 아니라 **실제 화면(캡처)과 개발 서버 기록**까지 확인한다.

## 2026-11-18 (3단계 배포)

### 틀림: 확인 코드를 입력해야 하는 로그인 명령을 입력창에서 실행하라고 안내함
- **틀린 것:** `supabase login`을 Claude Code 입력창에서 `! supabase login`으로 실행하라고 했다. 이 명령은 브라우저에서 받은 확인 코드를 터미널에 입력해야 끝나는데, `!`로 실행한 명령은 중간에 입력을 받지 못한다.
- **확인:** 브라우저에 확인 코드가 떴는데 넣을 곳이 없었다. `supabase projects list`가 계속 "Access token not provided"로 실패했다.
- **고친 것:** 별도 터미널에서 `supabase login`을 실행하고 거기에 코드를 넣었다. 로그인 정보는 Mac에 저장돼서 다른 터미널에서도 그대로 쓰였다.

### 틀림: 클라우드에 올릴 내용을 확인한다면서 로컬 DB를 확인함
- **틀린 것:** `supabase db push --dry-run`을 클라우드 확인용으로 실행했다. Supabase CLI 3.x는 기본 대상이 로컬이라, 로컬 DB를 대상으로 돌았다.
- **확인:** 결과 첫 줄이 `Target: local stack (127.0.0.1:54322)`였다. 대상을 확인하다가, 로컬 DB에만 남은 연습용 마이그레이션(`salary` 칸)도 발견했다. 파일은 지웠는데 DB에는 남아 있었다.
- **고친 것:** `--remote`를 붙여 다시 확인한 뒤 올렸다. `salary`는 코드 어디에서도 쓰지 않고 클라우드는 파일 기준이라 영향이 없음을 확인했다. 다음부터는 Supabase 명령 결과의 `Target:` 줄부터 본다.
